## 4. Порядок реализации

### Шаг 1 — сверить фактическую установку без движения

Сначала локально изучи код, сохранённые логи, конфиги и provenance. Если ROSMASTER доступен, прочитай версии/хеши собственной установки, службы, владельцев serial/camera, фактический boot, питания/feedback и последние ошибки. Не включай управление ради диагностики. Если он выключен, доделай всё доступное локально и затем попроси включить только ROSMASTER, сообщив конкретную цель.

Сопоставь развёрнутую версию с репозиторием, сохрани резерв собственной установки и точный список изменений перед развёртыванием. Не перепрошивай контроллер и не исправляй заводские нули/калибровки без отдельного предметного основания.

### Шаг 2 — закончить устойчивый control/data path

- Единое владение serial и камерой, явная передача Explorer ↔ прежняя система. Исключить одновременный моторный доступ двух backend. Одновременная независимая работа с другой платформой не должна искусственно блокироваться общей кнопкой выбора робота.
- Отдельные профили базы и руки; один ROSMASTER не может одновременно принадлежать двум несовместимым задачам.
- Сохранить понятный интерфейс выбранной 8090 в общем стиле Explorer: камера, свежие состояния, включение, STOP, режимы XYZ/суставы, клавиши/джойстик, запись. Убрать вводящие в заблуждение статусы, показать конкретную причину отказа.
- Разобраться с обрывами управления по фактическим логам. STOP и watchdog сохраняются. Не лечить разрывы отключением защиты, молчаливым бесконечным восстановлением движения или вымышленным feedback. После STOP, потери оператора/связи и перезапуска движение само не возобновляется.
- Запуск агента/камеры должен быть воспроизводимым и инертным. Историческая просьба о подъёме руки при загрузке не означает право отправлять неожиданные движения во время этой работы. Проверить прежнее поведение и сделать подготовку руки явной управляемой операцией с STOP; любые изменения автодвижения согласовать предметно.
- Зеркало сохранить и проверить существующий адаптер/знаки/пределы, не переписывать его заново. Не превращать его улучшение в условие готовности этапа B, если клавиатура/джойстик позволяют записывать показы. Подключение Leader и освобождение ресурсов Wristlab — только для конкретной согласованной проверки, не автоматически.

### Шаг 3 — данные и модель

- Проверить реальные camera timestamps/частоты, шестиканальный feedback, отправленные команды и времена их доступности. Не вычитать monotonic-часы разных машин без установленного преобразования. Неизмеренные latency/response — null + mask, а не ноль.
- Проверить актуальность замечаний раздела 9 главного задания: task timeout как failure; аппаратный/операторский abort отдельно; неизвестный measured_response_kind остаётся unknown; исследовательский маршрут идёт через собственный агент, не `leader8090.py`.
- Скопировать только необходимые реальные геометрические описания/коэффициенты в собственный provenance с исходными путями и хешами. Сверить установленную руку, направления, масштабы, пределы, положение камеры с MuJoCo. Производитель не доказывает соответствие кастомной руке.
- Для шасси определить, какая одометрия действительно измерена, а какая интегрирует команды; записать единицы, frames, направления осей, частоту, временную шкалу и маски недоступных датчиков. Не считать command-integral измеренной траекторией.
- Подготовить компактный отчёт для основного диалога и набор проверенных параметров. Изменения общей sim-модели выполнять отдельно и только с доказательствами; держать измеренное, опубликованное и предположенное раздельно. Идентификацию оценивать на независимых траекториях, ухудшившиеся параметры не применять.

### Шаг 4 — конечные пользовательские сценарии

Сначала программные проверки с fake transport и браузером, затем короткая физическая приёмка с отдельным подтверждением пользователя: свободное место, питание/зарядник и присутствие у выключателя. Старые разрешения из истории не считать подтверждением текущей сцены.

Для базы и руки по отдельности: направление, удержание/отпускание, STOP, скрытие вкладки, потеря связи, отсутствие самовозобновления. Просьбы пользователю — короткие, конкретные, по одной проверке; не просить включать весь парк. Логи отправленного STOP сами по себе не доказывают физическую остановку.

После успешного управления — по три настоящих показа каждой задачи:
1. база: подъезд к видимой цели и остановка в обозначенной зоне;
2. рука при неподвижной базе: кубик → коробка → отвести руку.

Проверить первый файл до следующих показов. Сохранить официальный LeRobotDataset и sidecar provenance: real/human, профиль, задача, scene/session, hashes, outcome, termination_reason, timestamps и маски. Неподвижные диагностические клипы не включать в демонстрации.

Довести сценарий «запись → просмотр/проверка качества → immutable dataset plan → подготовленное задание обучения → загрузка/проверка совместимости checkpoint → готовый запуск испытания». Не запускать обучение и автономное испытание без отдельного указания пользователя. Нет готовой политики — честный статус, не фиктивный успешный rollout. Не требовать десятков новых показов для окончания программной подготовки.

В конце проверить освобождение ресурсов и возврат прежнего управления без изменения его исходников. Попросить выключить ROSMASTER, если дальнейшая работа локальная: батарею не расходовать ожиданием.
