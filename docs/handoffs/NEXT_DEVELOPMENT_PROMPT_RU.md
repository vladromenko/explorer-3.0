## 1. Цель

Довести систему от «программная основа готова» до **проверяемого эксперимента
для одной статьи** с узкой гипотезой и достаточной мощностью. Новые
подсистемы не добавлять. Агентный слой (Qwen, память M0–M3, TaskGraph), DART,
ROS 2-шина остаются как есть, развитие заморожено: в первичный анализ статьи они
не входят.

**Научная формулировка** (заменяет §2 исходного задания по приоритетам):
- **H1 — первичная, в MuJoCo.** Оценщик пользы вмешательства G (условный
  причинный эффект, CATE), обученный на source-воплощениях с признаками
  измеренного отклика, на target-воплощении при бюджете 0/10/20 target-ситуаций
  даёт большую ценность правила помощи на секунду помощи, чем: (а) порог
  риска/ошибки исполнения, откалиброванный на том же target-бюджете; (б) тот же
  G только по командам; (в) target-only.
- **H2 — подтверждающая, на железе, одна метрика.** Sim-предобученный G + 20
  реальных калибровочных эпизодов ROSMASTER-руки лучше target-only по
  doubly-robust ценности правила на отложенных рандомизированных эпизодах.
  Мощность заранее рассчитана и честно указана.
- **Вклад в данные.** Открытый набор рандомизированных реальных вмешательств с
  вероятностями назначения, таймингами и исходами. Публикация — только с
  согласия пользователя.
- Эффект (3), улучшение автономного обучения от коррекций, — только в sim.
  На железе не заявляется.

## 2. Пакеты работ — программные, выполнять по порядку без ожидания железа

Каждый пакет: маленький коммит, тесты, запись в `STATE.md`, краткий отчёт.

### WP1. Предрегистрация и мощность
- `docs/PREREGISTRATION.md`: H1/H2, первичная метрика (DR-ценность правила
  на секунду помощи), первичный контраст, допустимые исключения (технический
  обрыв, аварийная остановка — отдельно, по ITT), правило остановки,
  exploratory-список. Хеш файла записывать в каждый `result.json` анализа.
- Обобщить `scripts/research_power.py`: оценщик с ошибкой, DR-оценка, блочная
  рандомизация. Выход — N для H1 (sim-ситуации) и H2 (реальные эпизоды).
  Таблицу вставить в предрегистрацию.
- Приёмка: пересчёт воспроизводим по seed; предрегистрация не ссылается на
  результаты test.

### WP2. Анализ (`research.py`, `research_value.py`, `datasets.py`)
1. Разбиение по каждому профилю отдельно; оценка через cross-fitting
   leave-one-group-out по связным группам сессия/расстановка. Фиксированный
   10 %-holdout оставить только для финального test.
2. Модели G: оставить T-learner как baseline. Добавить S-learner (pooled
   logistic с взаимодействием «назначение × признаки», фиксированная
   регуляризация, выбранная до данных) и DR-learner (pseudo-outcome при
   известной вероятности 0.5). Только scikit-learn/NumPy, без новых пакетов.
3. Перенос через source-prior: target-модель регуляризуется к
   source-коэффициентам (L2 к априорному среднему). Это отдельный вариант
   рядом с объединённым fit.
4. Ценность правил: добавить doubly-robust оценку к IPW; правило-порог
   калибровать на том же target-бюджете, что и G.
5. Отчёт содержит **все** запланированные варианты; `insufficient_data` с
   причиной — строка таблицы, а не пропуск. Первичный контраст выделен,
   остальные помечены exploratory.
6. Вариант признаков «пересечение доступных у source и target» как основной для
   переноса; маски, однозначно кодирующие тип робота, в нём запрещены.
- Приёмка: тесты на синтетике с известным CATE — DR/S-learner восстанавливают
  знак и ранжирование; IPW/DR сходятся к аналитической ценности (±0.015 при
  большом N); cross-fitting не допускает пересечения групп; сохранены прежние
  тесты `test_research*`.

### WP4. Симуляционное исследование, готовое к политике

## 3. Физическая часть — только с пользователем, по этапам

1. ROSMASTER: повтор приёмки (направления, отпускание, STOP, скрытая вкладка,
   потеря связи); 3 показа на задачу; чтение и проверка. Затем
   ≥50 успешных показов руки в ≥10 сериях с разными расстановками.
2. SO-101: короткий повтор приёмки; ≥50 успешных показов.
3. После разрешения на обучение: ACT по профилям; проверка политики на

4. Пилот H2: рандомизированные эпизоды по N из предрегистрации, блочная
   рандомизация, отдельные сессии. Аварийная помощь всегда важнее
   рандомизации.
5. Tank — только после аппаратной независимой остановки моторов (радио или
   реле питания, не зависящее от Pi/USB) и стендовой приёмки.
