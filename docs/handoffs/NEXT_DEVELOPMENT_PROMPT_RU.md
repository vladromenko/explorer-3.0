## Часть B. Научный дизайн, который реализуют пакеты

### B.1. Обозначения
- Эпизод i: признаки до решения X_i (8 значений из `research.FEATURES` и маски),
  назначение A_i ∈ {0,1} с известной вероятностью e = 0.5, исход
  Y_i ∈ {0,1} (success=1, failure=0; aborted — отдельно, по ITT, см. B.5),
  измеренная стоимость помощи C_i в секундах (human + switch, только у A=1).
- μ_a(x) = P(Y=1 | A=a, X=x). **G(x) = τ(x) = μ_1(x) − μ_0(x)** — условный
  средний эффект назначенной помощи (CATE), не индивидуальная метка.
- Правило π: X → {0,1}. Ценность V(π) = E[Y при следовании π].

### B.2. Гипотезы

**H1 — первичная, в MuJoCo (SIM).**
Target ∈ {rosmaster_pick_place_sim, rosmaster_dock_sim}. Source для руки:
so101_pick_place_sim; source для базы: tank_dock_sim. Бюджеты target-ситуаций
B ∈ {0, 10, 20, 50}. Правило помогает в доле q = 0.3 ситуаций с наибольшей
оценкой (одинаковый бюджет помощи). Первичный контраст:
Δ_H1 = V(π_{G-phys, transfer, B=20}) − V(π_{risk, target, B=20}),
где risk — порог по `tracking_error`, откалиброванный на тех же 20 target-
ситуациях. Вторичные: G-phys против G-commands; transfer против target-only;
кривая по B.
В симуляции у каждой ситуации известны *оба* исхода (ветви continue и
correction из одного состояния), поэтому V(π) вычисляется точно, без IPW.

**H2 — подтверждающая, на железе (REAL), две пары с общим target-роботом.**
H2a: SO-101 → ROSMASTER-рука (манипуляция). H2b: Tank → ROSMASTER-база
(`tank_dock` → `rosmaster_dock`, мобильный подъезд). Обе пары
предрегистрируются одинаково; поправка Холма на два первичных контраста.
Ниже формулы записаны для H2a, для H2b — те же с заменой профилей.
Пара SO-101 → ROSMASTER-рука. Оценщик: sim-предобученный G, дообученный
(source-prior, B.4) на 20 реальных рандомизированных эпизодах ROSMASTER-руки,
против target-only на тех же 20. Первичная метрика — DR-оценка
Δ_H2 = V̂_DR(π_{transfer}) − V̂_DR(π_{target-only}) при q = 0.5 на отложенных
рандомизированных эпизодах. N отложенных — из P3. Если мощность < 0.8,
результат подаётся как pre-registered pilot с CI, а не как подтверждение.

Если на одну из пар не хватает данных к сроку — она подаётся как
pre-registered pilot, вторая остаётся подтверждающей.
Почему Tank важен: два разных источника (рука и гусеничная база) позволяют
показать, что перенос работает не для одной удачной пары роботов, и проверить
кросс-переход «манипуляция ↔ мобильность» (G от SO-101 на базу ROSMASTER и
G от Tank на руку) как отрицательный контроль: ожидается слабый или нулевой
выигрыш, что подтверждает роль физической близости профилей.

**Исследовательские (exploratory):** кросс-переходы между манипуляцией и
мобильностью на железе, эффект (3) «коррекции улучшают последующее
автономное обучение» — только в sim, мобильные пары, калибровка вероятностей.

### B.3. Оценщики G (все — в `explorer3/research_estimators.py`, P4)
1. **T-learner** (текущий baseline): две `LogisticRegression` по ветвям.
2. **S-learner**: одна `LogisticRegression` на [X, A, A·X] с фиксированной
   регуляризацией C = 1.0 (заданной до данных); τ̂(x) = p̂(x,1) − p̂(x,0).
3. **DR-learner**: cross-fitted μ̂_0, μ̂_1 (по K групповым фолдам), псевдо-исход
   φ_i = μ̂_1(X_i) − μ̂_0(X_i) + A_i(Y_i − μ̂_1(X_i))/e − (1−A_i)(Y_i − μ̂_0(X_i))/(1−e),
   затем `Ridge(alpha=1.0)` φ ~ X; τ̂ — прогноз Ridge, обрезанный в [−1, 1].
4. **Source-prior (перенос)**: S-learner target с штрафом
   λ‖β − β_source‖² вместо ‖β‖². Сетка λ ∈ {0.1, 1, 10} фиксирована в
   предрегистрации; выбор λ — внутренним leave-one-group-out только по
   target-train. Реализовать через `scipy.optimize.minimize` (L-BFGS) на
   логистической потере. Признаки стандартизовать по *source*-train, чтобы β
   были сопоставимы; это записать в артефакт.
5. **Risk-baseline**: правило «помогать, если tracking_error > t», t выбирается
   по target-бюджету. Если tracking_error недоступен — baseline по
   `command_change` (явно пометить).

### B.4. Оценка ценности правил
- **REAL**: DR-оценка (μ̂ — cross-fitted):
  V̂_DR(π) = mean_i[ π(X_i)·(μ̂_1 + A_i(Y_i−μ̂_1)/e) + (1−π(X_i))·(μ̂_0 + (1−A_i)(Y_i−μ̂_0)/(1−e)) ].
  Рядом — нормированный IPW (уже есть в `research_value.py`).
- **SIM**: V(π) = mean_i Y_i(π(X_i)) по известным парным исходам.
- **Стоимость.** Отчёт для каждого правила: доля помощи, оценка человеко-секунд
  ĉ = (доля помощи) × (среднее измеренное C у A=1), прирост
  (V(π) − V(never)) / ĉ. Отсутствующий тайминг — null, не ноль.
- **CI.** Кластерный бутстрап по связным группам (сессия ИЛИ сцена), 2000 повторов,
  seed 1000. Если групп < 5 — CI не публиковать, писать «групп недостаточно».

### B.5. Исключения и исходы
- ITT: анализируется назначение, а не факт помощи. Нарушение назначения (помощь
  в A=0, нет помощи в A=1) — флаг `deviation`, эпизод остаётся в анализе.
- Aborted, технический обрыв, аварийная помощь — отдельная таблица attrition.
  Первичный анализ: complete-case по success/failure. Чувствительность: worst-case
  (aborted = failure в ветви, где это ухудшает первичный контраст).
- Предварительно заданные критерии технического исключения (обрыв связи до
  точки решения, отказ записи) — в предрегистрации. Других исключений нет.

### P1. Рандомизированный пилот SO-101 (КРИТИЧЕСКИЙ дефект)

**Зачем.** SO-101 и Tank — два робота-источника для H2a и H2b. Пилот Tank
есть, но у него нет измеренного отклика; на SO-101 пилот невозможен:
- `tank_pilot.accepted_study` отклоняет любой профиль, кроме `tank_dock`, хотя
  `session.py:68` вызывает его для всех;
- `TankPilot.tick` берёт `profile('tank_dock')['feature_scales']` для любого
  робота;
- `TankPilot.observe` ставит `state_valid=False`, поэтому у SO-101 не
  появляются измеренные признаки отклика, хотя `hardware.py` даёт
  `measured_joint_position`;
- в `session.py` фаза `safety` подаёт `[0., 0.]` (две оси шасси), фаза `human` —
  `control.base_action()` (клавиатура шасси). Для руки нужно удержание текущей
  позы и коррекция через Leader;
- в испытании политики `HardwareSource(teleoperate=not bool(provider))` вообще
  не читает Leader.

**Что изменить.**
1. Новый `explorer3/pilot.py` (Tank-модуль оставить как тонкую обёртку для
   совместимости импорта):
   - `accepted_study(ident, plan)` проверяет `study['profile'] == plan['profile']`
     и `plan['kind'] == 'policy'` для профилей
     {so101_pick_place, tank_dock, tank_dock_rgbd_lidar}; остальные проверки
     сохранить;
   - `class Pilot(study, trial_id, session_id, scene, profile_name, adapter)`,
     где `adapter` задаёт роботно-специфичное поведение:
     `hold_action(observation)` и `human_action(observation)`;
   - `tick` использует `profile(profile_name)['feature_scales']`;
   - `observe(sample)` сохраняет `state_valid` и `measured_response_kind`
     из sample как есть (у Tank там остаётся команда-оценка, и `research.features`
     её не возьмёт).
2. Адаптеры:
   - `TankAdapter`: hold → `[0., 0.]`, human → `control.base_action()`
     (поведение как сейчас), плюс **измеренный отклик**: сейчас у Tank
     `state_valid=False`, и G-phys на нём не считается. Брать из штатных
     топиков (как `agents/tank/telemetry_probe.py`, только подписка):
     угловая скорость IMU (рыскание) и изменение дальности лидара в переднем
     секторе ±10° → `measured_response_kind='imu_yaw_rate+lidar_range'`,
     `state_valid=True`, только если оба потока свежее 0.2 с. Колёсную
     скорость командой не подменять. Те же признаки — у ROSMASTER-базы и в
     `tank_dock_sim`/`rosmaster_dock_sim`, иначе перенос G-phys между базами
     сравнивает разные величины;
   - `So101Adapter`: hold → последняя измеренная поза follower
     (`observation['observation.state']`, захват не менять); human → действие
     Leader через существующий тракт `HardwareSource` с фазой `aligning`
     (ограниченное сближение команды от позы follower к позе Leader, порог
     2°/3° как в `hardware.py:489`). Leader не приводится в движение
     автоматически: оператор сам подводит его, пока follower стоит.
3. `session.py`: в испытании политики со study открывать Leader на чтение
   (`teleoperate=True`), но пока фаза `policy`/`resumed`, Leader-команды не
   подаются. При смене фазы → `provider.reset()` (очистить ACT chunk); при
   `resumed` — новый chunk с текущего наблюдения. В sample писать
   `pilot_phase`, `command_source`.
4. Признак «оператор начал»: для руки — изменение позы Leader > 2° от момента
   уведомления, а не `abs(action) > 1e-6`.
5. UI SO-101 (страница испытаний): баннер фазы (политика / удержание /
   «Ваша коррекция, осталось N с» / политика продолжает), кнопки
