## 0. Вердикт в пяти строках

1. **Тема актуальна, ниша пока не занята.** Не найдено работ, где оценивается
   *польза* человеческого вмешательства, т. е. условный причинный эффект
   (CATE), на реальных роботах с рандомизацией и где этот оценщик переносят между
   разными платформами. Ближайшие работы закрывают соседние вопросы: RESCUE
   (ценность вмешательства, только симуляция), FARM (перенос *детектора провала*
   между роботами, включая SO-101), ARMADA/Fleet-DAgger (распределение оператора).
2. **Программная база сильная, но научных данных ноль.** Рандомизированных
   эпизодов 0, исследований 0, обученных политик 0 (только smoke на 50 шагов).
   Реальных успешных показов всего 5: SO-101 — 3, ROSMASTER-база — 1, Tank — 1.
3. **Главная методологическая проблема — статистическая мощность.** Пилот на
   ≥20 эпизодов в ветви (≈40 на профиль) даёт около 10 % шанса увидеть
   преимущество даже *идеального* правила помощи. Нужны сотни
   рандомизированных эпизодов на целевой профиль (см. §3.1). Сравнение «с
   физическими признаками / без них» на железе практически недостижимо.
4. **План переноса опирается на заблокированный Tank.** Схема «источник SO-101
   + Tank → цель ROSMASTER» сейчас невыполнима: у Tank не закрыта проблема
   STOP/USB. Пара мобильных платформ без Tank не складывается.
5. **Объём разросся.** Агенты, Qwen-VL, общая память M0–M3, DART, ROS 2-шина,
   Fleet-распределение размывают одну проверяемую гипотезу. Для статьи нужно
   резко сузить объём и перенести основную причинную часть в симуляцию, где
   ветвление из точного состояния даёт парные контрфактические исходы.

## 1. Что заявлено в исследовании

Вопрос (`RESEARCH_PROTOCOL.md`): помогает ли короткая история *измеренного*
отклика на команды переносить оценщик пользы вмешательства
G(h,d) = P(успех | коррекция после задержки d, h) − P(успех | без коррекции, h)
с SO-101 и Tank на ROSMASTER при ограниченном времени оператора? Три эффекта
разведены корректно: (1) коррекция помогла текущей попытке; (2) оценщик
перенёсся; (3) коррекции улучшили последующее автономное обучение.

**Что сделано хорошо и стоит сохранить:**
- Рандомизация на уровне эпизода, записанная вероятность назначения 0.5,
  анализ по назначенной ветви (intention-to-treat), без выдуманного второго
  исхода.
- Признаки — только прошлое до момента решения; маски отсутствующих измерений;
  команда не выдаётся за измеренный отклик; robot ID не используется. Есть
  базовый вариант `commands`, в котором отклик скрыт: он служит общим для всех
  роботов набором сенсоров.
- Разбиение по связным группам сессия/расстановка, нормировка только по train,
  зафиксированные хеши, aborted-исходы не превращаются в failure.
- Ценность фиксированных правил оценивается через IPW по назначенной вероятности,
  а не только Brier (`research_value.py`).
- Атрибуция заимствований (`RESEARCH_REUSE.md`) честная: «adapted»,
  «DART-inspired», «не воспроизведение».

## 2. Актуальность и новизна

| Работа | Что делает | Чем отличается от Explorer |
|---|---|---|
| [RESCUE, 2610.13516](https://www.emergentmind.com/papers/2610.13516) | Мониторы VLA судят по *ценности* тревоги, а не точности; 128 340 ветвей, LIBERO | Только симуляция, scripted recovery, без человека и без переноса между роботами. **Главный конкурент по идее «ценность, а не детекция»** — нужно явно сослаться и отличиться реальными рандомизированными данными |
| [FARM, 2609.11445](https://arxiv.org/abs/2609.11445) | Readout провала поверх замороженной world model; перенос между PIPER X, SO-101, Franka | Предсказывает *провал*, а не *пользу помощи*. **Главный конкурент по переносу между роботами**, включая ту же SO-101 |
| [AutoIntervene, 2608.07065](https://arxiv.org/abs/2608.07065) | Переключение ACT↔оператор по памяти поддержки, пороги по квантилям | Один робот, кода нет; в Explorer — адаптированный baseline |
| [ARMADA, 2510.02298](https://arxiv.org/abs/2510.02298) | Детектор FLOAT + один оператор на несколько роботов | Детекция + распределение, не оценка пользы; [код](https://github.com/Virlus/armada) |
| [Fleet-DAgger](https://proceedings.mlr.press/v205/hoque23a.html), [ThriftyDAgger](https://proceedings.mlr.press/v164/hoque22a.html), [Sirius-Fleet](https://arxiv.org/abs/2410.22689) | Распределение внимания оператора, risk/novelty | Приоритет по риску/новизне, а не по причинному эффекту помощи |

**Вывод.** Узкая формулировка остаётся свободной: *рандомизированная оценка
условной пользы реального человеческого вмешательства и её перенос между
воплощениями при фиксированном бюджете целевых эпизодов*. Писать «мы не нашли
работ», а не «впервые»: поиск не исчерпывающий. Самый сильный и редкий вклад —
**открытый набор рандомизированных реальных вмешательств с вероятностями
назначения и таймингами**. Такого почти нет, и он полезен независимо от знака
результата.

**Чего не хватает в позиционировании.** G — это CATE, а две логистические
регрессии — T-learner. Строгий рецензент спросит про стандартные методы:
мета-learners (Künzel et al., 2019, PNAS), DR-learner (Kennedy, 2023),
doubly robust оценка ценности политики (Dudík et al., 2011), policy learning по
рандомизированным данным (Athey & Wager, 2021, Econometrica), переносимость
эффекта между популяциями (Pearl & Bareinboim). Без этой терминологии работа
выглядит как изобретение заново.

## 3. Критические методологические проблемы

### 3.1. Мощность реального эксперимента (блокирующая)

`scripts/research_power.py` моделирует пилот так: помощь назначается с
вероятностью 0.5, и сравнивается целевое правило с *идеально известным*
признаком против случайного правила 50 %. Реальная мощность будет **ниже**:
в модели оценщик не ошибается.

| Макс. польза помощи | N=40 | N=80 | N=160 | N=320 | N=640 |
|---|---|---|---|---|---|
| +0.2 | 0.06 | 0.06 | 0.11 | 0.21 | 0.30 |
| +0.3 | 0.14 | 0.12 | 0.24 | 0.29 | 0.56 |
| +0.4 | 0.10 | 0.20 | 0.35 | 0.56 | 0.86 |

Протокольные ≥20 эпизодов в ветви — это строка N=40, мощность около 10 %.
Абсолютное преимущество правила невелико (+3…+6 п.п.), потому что правило и
случайный выбор совпадают на половине эпизодов. Разница «G с физикой против G без
физики» ещё меньше, и для неё нужны тысячи эпизодов на профиль.

**Следствие.** Основные причинные сравнения (H1, перенос, абляция физических
признаков) нужно проводить в MuJoCo. Там ветвление из точного состояния даёт
*парные* исходы одной и той же ситуации, и дисперсия на порядки ниже.
Реальный эксперимент — это калибровка и проверка sim-to-real с одной заранее
зарегистрированной первичной метрикой и честно широкими интервалами. Ещё одна
возможность — увеличить число реальных эпизодов за счёт коротких попыток и
блочной рандомизации внутри сцены.

### 3.2. Цепочка предпосылок не выполнена
- Нет ни одной обученной политики. Чтобы G была идентифицируема, политика в
  точке решения должна давать **промежуточный успех, примерно 30–70 %**. При
  0 % или 95 % польза помощи почти константа. Протокол не содержит шага
  «подобрать условия так, чтобы успех был в этом диапазоне» и заранее
  зафиксированного правила такого подбора.
- Обучение ACT на Homebrain идёт 0.8 с/шаг, это ≈22 ч на 100k шагов и профиль.
  Четыре политики — около 90 ч. Эффект (3) требует ещё по дообучению на каждый
  метод из одной точки, то есть сотни часов. **На Jetson эффект (3) на железе
  нереалистичен.**
- Обучение в симуляции запрещено оператором. Поэтому в sim нет политики с
  промежуточным успехом: PPO даёт 0/20, ACT после 50 шагов — 0/3. Без такой
  политики исследование на ветвях не может начаться. **Это решение
  пользователя, а не инженерная задача.**

### 3.3. Дизайн переноса
- Tank заблокирован, поэтому источник фактически один — SO-101. Нужен план Б:
  (а) SO-101 → ROSMASTER-рука как основная реальная пара манипуляторов;
  (б) мобильный перенос Tank → ROSMASTER-база только в симуляции, пока Tank
  не принят.
- Маски наличия сенсоров выдают тип робота: у Tank нет энкодеров. Вариант
  `commands` это частично закрывает. Нужен ещё вариант «одинаковый набор
  признаков у source и target» как основной для переноса.
- Перенос сейчас — это простое объединение source и target в одном fit. Более
  сильный и стандартный вариант — **source-модель как априорное распределение**
  для target: байесовская или L2-регуляризация к source-коэффициентам. Именно на
  10–20 целевых эпизодах это даёт разницу.
- В sim «помощь» — scripted privileged DockExpert, в реальности — человек.
  Перенос G из sim в real смешивает смену домена и смену вида помощи. В sim
  нужен хотя бы один вариант помощи, похожий на человеческий: воспроизведение
  записанных человеческих коррекций или teleop в sim.

### 3.4. Статистика в коде (`research.py`, `datasets.py`)
1. `grouped_split` откладывает в test 10 % групп *по всем профилям сразу*. При
   пилотных объёмах у целевого ROSMASTER в test попадает около 1 группы, и CI
   недоступен. Нужны разбиение по каждому профилю отдельно и **cross-fitting
   (leave-one-group-out)** для оценки: при малых данных он использует все
   эпизоды, а не 10 %.
2. При бюджетах 10/20 `fit(..., minimum_per_arm=2)` обучает 16 входов (8
   признаков + 8 масок) на ~5 эпизодах в ветви. Варианты, где в ветви нет обоих
   исходов, молча становятся `insufficient_data`. В итоге в отчёт попадает
   *отобранное* подмножество вариантов. Нужны фиксированная регуляризация,
   pooled-модель с взаимодействием «назначение × признаки» (S-learner) или
   DR-learner и обязательная отчётность по всем запланированным вариантам.
3. Ценность правил сейчас оценивается только чистым и нормированным IPW.
   Добавить **doubly robust**: при рандомизации 0.5 он несмещён и заметно
   снижает дисперсию.
4. Множественные сравнения: 2 набора признаков × 3 бюджета × transfer/target-only ×
   профили × 5+ правил, и нет одной первичной гипотезы. Нужна предрегистрация:
   одна первичная метрика, один первичный контраст, остальное — exploratory.
5. Порог `threshold:tracking_error` подбирается на train, куда входят source-
   роботы с другим масштабом ошибки. Для честного baseline нужен порог по
   target-калибровке того же бюджета.
6. Решение принимается в фиксированный момент (`decision_after_s`), а не по
   запросу помощи. Оценка корректна для «решения в момент t». При развёртывании
   как планировщика запросы приходят в другие моменты, и распределение
   состояний будет другим. Это ограничение нужно прямо записать.
7. Пилотный старт ROSMASTER (`trial_start` в `rosmaster-console.html`) передаёт
   `scene`, но **не передаёт `collection`**. Все пилотные испытания дня
   попадают в одну автоматическую сессию, т. е. в одну группу. Для записи
   показов поле «Сессия сбора» уже есть.

### 3.5. Симуляция
- Параметры ROSMASTER не идентифицированы: реальных записей движения нет,
  инструмент `sim/rosmaster_sysid.py` ждёт данных. Для SO-101 sysid ухудшил
  отложенную ошибку (0.00566 → 0.00595 рад), параметры не применены. Пока sysid
  нет, любое утверждение sim-to-real — гипотеза.
- Диапазоны рандомизации заданы «assumed». Их нужно сузить по реальным логам
  до основной серии.

## 6. Рекомендуемая переформулировка статьи

**Рабочее название:** «Transferring intervention-value estimates across robot
embodiments: randomized real-robot evidence with simulation pre-training».

- **H1 (sim, первичная).** G с признаками измеренного отклика, обученный на
  source-воплощениях, на target при бюджете 0/10/20 даёт большую ценность
  правила помощи на секунду человека, чем (а) порог риска, (б) G только по
  командам, (в) target-only. Парные ветви, сотни ситуаций, CI по сценам.
- **H2 (real, подтверждающая, одна метрика).** Sim-предобученный G + 20
  реальных калибровочных эпизодов ROSMASTER-руки предсказывает пользу помощи
  лучше target-only. Метрика — DR-ценность правила на отложенных рандомизированных
  эпизодах. Заранее заявленная мощность честно указывается.
- **Вклад в данные:** открытый набор рандомизированных реальных вмешательств
  (3 робота, вероятности, тайминги, исходы).
- **Вынести из этой статьи:** агентный слой (Qwen, память M0–M3, TaskGraph),
  DART, ROS 2-шину, эффект (3) на железе. Их можно оставить в системе как
  инфраструктуру или для отдельной работы.
